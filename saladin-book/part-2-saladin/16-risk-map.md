# Chapter 16 — Risk Map

The development-risk register for the whole Part 2 program. Scales: likelihood
(L) and impact (I) each Low/Med/High. **EWI** = early-warning indicator. Ordered roughly by
severity within each group.

## 16.1 Correctness & protocol risks

| # | Risk | L | I | Mitigation | EWI |
|---|---|---|---|---|---|
| R1 | **State archival expires UTXO/nullifier entries.** Soroban persistent entries have TTLs; expired = archived. Nuance that saves us: archived persistent keys are *not absent* — transactions touching them **fail until restored**, so the failure is **liveness (stuck transfers, blocked refunds), never silent double-spend** — *provided* contracts never treat "not found" as "never existed" and never keep consensus-critical facts in `temporary` storage. ◐ **Mitigations shipped**: `extend_ttl` on every SNoto/SZeto write, the `ttlJanitor`, and the submitter's automatic restore preamble are all implemented and hold up analytically (ch. 13 §13.2). **Not yet done**: an actual forced-archival chaos test — the mechanism has never been deliberately exercised end to end. | H | H | `extend_ttl` on every write; node `ttlJanitor`; automatic restore preamble in the submitter; code-review rule "no temporary storage for state/nullifier/lock data"; forced-archival chaos tests (still outstanding) | any `entryArchived` failure on testnet; TTL-remaining metric below threshold |
| R2 | ✅ **CLOSED.** **Per-tx resource limits break the UTXO transaction shape.** Footprint entries, read/write bytes, CPU instructions are far tighter than EVM gas; a 50-input transfer trivial on Besu may not fit, and Groth16 verification consumes a large fixed budget first. **M0 spike run (chapter 13 Phase 5)**: verify+N flat nullifier writes cost ~29M CPU instructions regardless of N (Groth16's pairing check dominates; instructions are not the binding constraint there) - `write_entries` is. **Correction**: this was originally written against a 50-entry mainnet ceiling, sourced from `soroban-sdk`'s own `NetworkInvocationResourceLimits::mainnet()` test helper — that constant is stale by the SDK's own admission ("not pulling the values dynamically"); a live check of Stellar mainnet's real `tx_max_write_ledger_entries` network setting shows 200, not 50 (re-confirmed independently via R21's own cost spike, ch. 14 §14.3). Doesn't change this risk's own conclusion below, since the *actual* binding constraint turned out to be CPU instructions from Merkle-tree maintenance, not write-entry count. **A second, larger cost was found once EVM-parity on-chain Merkle-tree maintenance was factored in** (see R3): a single 64-level incremental-tree leaf insert (matching `@iden3/contracts`' `SmtLib.addLeaf`, real on-chain Poseidon calls) costs ~94M CPU instructions - **per output commitment**, not per transaction. **Resolution shipped, not just chosen**: `szeto/src/lib.rs` enforces `MAX_SAFE_BATCH_OUTPUTS = 5` as a hard on-chain cap (ch. 13 §13.3), the measured-safe batch size — full EVM-parity batch sizes (10+) are out of scope by design, not an open question. | ~~H~~ Closed | ~~H~~ Closed | **Week-1 benchmark spike (M0) - done**; cap enforced on-chain (done); entry-per-state storage (fine-grained footprints); assembler-level transaction splitting remains future work only for anything needing more than the enforced cap | — |
| R3 | ✅ **CLOSED.** **Groth16/Poseidon parameter mismatch.** circomlib's Poseidon constants/arity vs Soroban's host Poseidon; snarkjs verifying-key serialization; G2 endianness. Late discovery forces in-Wasm Poseidon (budget blowout → collides with R2) or circuit regeneration + new trusted setup. **M0 spike run**: no mismatch found - the official `stellar/rs-soroban-poseidon` crate reproduces `go-iden3-crypto`'s Poseidon output bit-for-bit at both arities EVM Zeto's on-chain `SmtLib` actually uses. A real, unmodified Zeto proof (`anon` circuit) verified `Ok(true)` through a ported BN254 Groth16 verifier running inside a real (non-mocked) Soroban host, and a Rust-side test (`tree_matches_go_lfdt_paladin_smt_implementation`) confirms tree-root parity against the Go SMT implementation directly (ch. 13 §13.3) — not just a one-off spike result. | ~~M~~ Closed | ~~H~~ Closed | Week-1 vector test - **done**; verify one real Zeto proof in the official verifier example - **done**; ongoing root-parity test in CI (`tree_matches_go_lfdt_paladin_smt_implementation`) | — |
| R4 | **Event-retention window vs indexer downtime.** stellar-rpc keeps 24h–7d; an outage or fresh sync beyond retention gaps the domain state view. ⚠️ **Mitigation not yet built**: the fail-loud/backfill behavior described here is still ch. 12's own "what's left" item — retention-gap handling exists only as a design, not as shipped code. | M | H | history-archive/RPC-indexer-based backfill designed but **not yet implemented** (ch. 12 §12.4); self-hosted RPC at max retention; aggressive checkpointing; alert at 25 % of retention lag | indexer-lag trending up; gap error in the 48h-downtime soak |
| R5 | **Simulation/footprint race under contention.** Contested entries changing between simulate and inclusion fail the tx. ✅ **Mitigation shipped**: `ActionOnStale`'s re-simulate-and-rebuild path is implemented (ch. 12 §12.2) — the residual risk is that it's never been measured under real contention/load, not that it's missing. | M | M | re-simulate-on-retry loop (implemented); contract design avoids hot shared entries (per-state keys); the sequencer already serializes spends per domain | footprint-mismatch failures >1 % in load tests (no load test run yet) |
| R6 | **Sequence-number head-of-line blocking.** One stuck tx blocks everything behind it on a source account; EVM nonce-gap logic doesn't map. ◐ **Partially mitigated**: the channel-account pool is implemented and proven live (real Testnet demos use it); fee-bump escalation is not yet built (ch. 12 §12.2), so a genuinely stuck submission still has no automatic recovery today. | H | M | channel-account pool (ch. 12) — **shipped**; fee-bump escalation — **not yet built**; pool size monitored/configurable | `txBAD_SEQ` in load tests; latency correlating with queue depth |
| R7 | **Auth-entry expiry mid-flight.** `signature_expiration_ledger` passes while a tx is queued → endorsement must be redone; no EVM analogue. ⚠️ **Correction: the re-endorsement path is not built, not "tested."** Ch. 12's own "what's left" is explicit that this has no sequencer-side implementation yet — the mitigation below is a design, not a shipped mechanism. | M | M | generous expiration budgets; submitter detects and bounces to sequencer for re-endorsement — **design only, not yet implemented**; expirations sized vs worst-case fee-retry cycles | re-endorsement counter non-zero in steady state |
| R21 | ✅ **CLOSED.** **Sente's on-chain `root` was positional, not content-addressed — no independent structural backstop against stale/wrong endorsed state.** Unlike Pente's `_unspent` mapping (which independently checks the *actual* current account-state hash regardless of what any endorser believed), `SentePrivacyGroup`'s `root` was a bare hash chain — `sha256(old_root, tx_id[, invocation_digest])` — with no accumulator over the underlying `SenteEntry` set: total ordering was enforced (a stale/replayed `old_root` recomputes the wrong signed payload and fails verification), but a transition's claimed business-state effects were checked exactly once, at endorsement time, with no second, independent on-chain line of defense. **Fix shipped, not just designed** (ch. 14 §14.3): `transition` gained `inputs`/`outputs: Vec<BytesN<32>>` — content-addressed commitment hashes (`domain::entry_commitment`, a self-contained hash independent of Paladin core's own separate state-ID scheme) checked against a real, persistent `Unspent` set, the direct translation of `PentePrivacyGroup.sol`'s own `_unspent` mapping (`sente: input not available`/`sente: output already unspent`). Empty (and free) for a root-only transition — strictly additive, no behavior change for any existing caller. `endorse_transaction` independently recomputes and cross-checks these commitments from its own re-execution before signing, closing exactly the gap: a bug shared across every endorser's plugin binary can no longer silently corrupt a group's private ledger with nothing on-chain able to catch it. New contract-level tests (`transition_rejects_input_never_created`, `transition_rejects_double_spend_of_same_input`, `transition_rejects_output_already_unspent`) plus the full existing Soroban and Rust-plugin test suites (including the cross-process `two_node_invoke`/`divergence` tests) all pass. **Cost spike run** (`soroban/contracts/sente/src/bench_test.rs`, ch. 14 §14.3, R2's own measure-don't-estimate methodology): `write_entries = 2N + 1` for N touched business entries, confirmed via real Soroban invocation-resource metering — CPU instructions are never the binding constraint (>94% headroom at N=120). **Correction**: the safe ceiling is N=99, not the originally-reported N=24 — that earlier number used `soroban-sdk`'s own `NetworkInvocationResourceLimits::mainnet()` test helper (`write_entries: 50`), which its own doc comment admits is not pulled dynamically and is stale; a live check of Stellar mainnet's real `tx_max_write_ledger_entries` network setting shows 200, not 50 (the same stale constant this risk's own R2 write-up above also used). N=100 exceeds the real limit. No enforced cap shipped yet — not urgent, since every current caller (including the repo demo) is root-only and touches zero business entries — but worth adding once Sente's business-invocation path sees real use, re-checking the live network setting at that time since it's validator-voted, not fixed. | ~~L–M~~ Closed | ~~H~~ Closed | Real `Unspent` set + `inputs`/`outputs` commitments — **shipped, tested, and cost-benchmarked**; a `MAX_SAFE_TOUCHED_ENTRIES`-style enforced cap (mirroring SZeto's own `MAX_SAFE_BATCH_OUTPUTS`) is future work once business invocations see real use; S4's determinism audit/chaos suite is separate, unrelated hardening | write_entries approaching the live mainnet `tx_max_write_ledger_entries` setting in a real business-invocation transition |
| R22 | **Sente's private simulation runs against a frozen, fake `LedgerInfo`, not the real chain's current one.** `assemble_transaction`/`endorse_transaction` (`domains/sente/crates/sente/src/domain.rs` — the real production path every business invocation goes through, not test-only code) both call `soroban_env_host::e2e_testutils::default_ledger_info()`, a hardcoded SDK test fixture (`sequence_number: DEFAULT_LEDGER_SEQ`, `timestamp: 12345678` — literally that fixed number) returned identically on *every* invocation, regardless of when it's actually assembled in real wall-clock time. A privately-hosted contract's own `env.ledger().sequence()`/`.timestamp()` calls therefore never see real, live chain state. **Independent of S4's protocol-version-dispatch work** (ch. 14 §14.3) — even with correct multi-version host dispatch, these specific fields would still be fake; the gap is in the *source* of the pinned value, not which host version interprets it. Confirmed concretely via the institutional repo demo (ch. 18): `agreeRepoTerms`'s own `maturityLedger` value is computed once, stored privately, and never referenced again anywhere — the "far leg matures the repo" narration is a purely human-paced UI pause (`pauseForDemo`), not an enforced condition; no current or plausible future Sente-hosted business logic can enforce a real time/ledger-based condition until this is fixed. | M | M | Derive `LedgerInfo` from the real, live chain at assembly time (the same live query Stellar's own `simulateTransaction` preflight already performs for ordinary transactions, ch. 12 §12.1) instead of the hardcoded fixture — the pin-at-assembly/verify-at-endorsement mechanism itself is already correct, only the value's source needs to change; not urgent today since no shipped business logic depends on real ledger time yet | any Sente `invoke` business logic referencing `env.ledger()` for a real decision (e.g. a genuine maturity/expiry check) |

## 16.4 Timeline sanity check

Critical path: **BLI (M1–M2) → Stellar submitter/indexer (M3) → SNoto (M4)**, with SZeto (M5) off
the critical path and Sente (M6) off the MVP entirely (R14). Ch. 15 §15.2 has the current,
milestone-by-milestone remaining-effort breakdown (~15.5 em across M1–M7, ~5 em of which needs
human-originated design rather than being agent-executable) — this section's job is the sanity
check: does that number survive contact with this register's remaining open risks?

- R2 and R3 (resource limits, Groth16/Poseidon parity) — the two risks that could have blocked
  SZeto's whole design outright — are both **closed**, not open items to price for anymore: the
  M0 spikes ran, found real numbers, and those numbers are enforced in shipped code (§16.1). The
  timeline no longer needs to hedge against either surprising it.
- What's left to price: **R1** (archival/liveness correctness — mitigations shipped, the chaos
  test itself isn't) and **R8** (upstream mergeability of the M1 sweep — hasn't started, so
  unproven either way). Any plan promising materially less than ch. 15's own total has not priced
  these two.
